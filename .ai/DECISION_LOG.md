It enforces a strict, deterministic schema of three metrics: `structural_completeness` (derived from failure severity), `uncertainty_confidence` (derived from normalized uncertainty score), and `explanation_richness`. Crucially, `explanation_richness` measures information coverage structurally by analyzing how many core domain namespaces ("decision", "uncertainty", "failure", "verification") are represented within `ExplanationSection.identifier`s, ensuring complete implementation-agnostic evaluation independent of rendering styles, phrasing, or string lengths. | Approved |
| Architecture | ADR-068: Evaluation Profiles | M14.3 finalizes the Evaluation subsystem by introducing `EvaluationProfile` and `EvaluationProfileRegistry`, mirroring the established Arbiter framework pattern. `EvaluationProfile` binds exactly one `EvaluationDefinition` with a compatible `BaseEvaluator`, validating compatibility exclusively during construction via `model_validator(mode="after")`. The registry guarantees `min_length=1`, statically detects duplicate `profile_id`s, and exposes an O(1) resolution interface through a private immutable index, ensuring `Evaluator` remains purely stateless and profile-agnostic. | Approved |
| Architecture | ADR-069: Pipeline Orchestrator | M15.1 introduces `ArbiterPipeline`, the top-level orchestrator that sequentially binds the M1–M14 stages. It utilizes Just-In-Time (JIT) profile resolution via constructor-injected registries to ensure strict dependency locality and extensible routing while remaining perfectly stateless after construction. Intermediate states are explicitly hidden, and the pipeline returns the final native `EvaluationResult` which, via nested object identity, preserves complete O(1) traceability back to the initial execution inputs. | Approved |
| Architecture | ADR-070: FastAPI API Layer | M15.2 introduces Arbiter's HTTP API layer. The API utilizes Dedicated API Transport Models (DTOs) to establish a strict anti-corruption layer, shielding internal domain models from external network contracts. The API layer acts as a thin adapter, extracting `ArbiterPipeline` exclusively from application state (`request.app.state.pipeline`), thereby completely deferring formal dependency injection (e.g., FastAPI's `Depends`) and configuration wiring to M15.3. A global exception handler maps core `ArbiterError` subclasses directly to HTTP 400 responses, preventing internal stack traces from leaking to API consumers. | Approved |
| Architecture | ADR-071: Dependency Injection & Configuration | M15.3 establishes a deterministic, stateless composition root in `src/core/bootstrap.py`. It utilizes subsystem-specific registry factories (e.g., `build_decision_registry(config)`) coordinated by a thin top-level `build_pipeline(config)` function. This enforces strict fail-fast startup semantics by binding and validating all concrete strategies, configurations, and profiles synchronously during the FastAPI `lifespan` initialization. This guarantees a mathematically pure `ArbiterPipeline` with completely immutable DI routing while deliberately avoiding dynamic/global dependency magic. | Approved |
| Architecture | ADR-072: End-to-End Integration Tests | M15.4 establishes the integration testing architecture. Domain tests assert absolute mathematical ownership-chain identity (`is`) directly against native objects returned by `ArbiterPipeline.execute()`. HTTP tests validate router exception translation, payload schemas, and aggressive application `lifespan` startup failures. To preserve structural integrity and determinism, no business logic is mocked; tests rely entirely on terminal dummy ML models constructed explicitly by the composition root. | Approved |
| Architecture | ADR-073: Production Readiness | M15.5 finalizes the core production architecture. The health endpoint is bifurcated into `GET /health/live` (event loop heartbeat) and `GET /health/ready` (stateless verification of a successful fail-fast boot sequence without ongoing dynamic validation). Internal `Exception` (HTTP 500) payloads are perfectly obfuscated from API consumers, retaining stack traces only in the infrastructure-focused structured logs. | Approved |
